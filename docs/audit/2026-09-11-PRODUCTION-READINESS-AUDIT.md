# Аудит продакшн-готовности — OpenStream Engine

> Дата: 2026-09-11 · Область: OpenWrt-контур (init, ucode RPC, nftables, dnsmasq, упаковка) + Rust-ядро
> Метод: чтение кода и сверка с документацией. Живого роутера не было — динамические проверки не выполнялись, это отмечено явно.
> Связанный документ: [2026-09-11-README-AUDIT.md](2026-09-11-README-AUDIT.md)

## Итоговый вердикт

**Не готово к продакшену. Оценка: 3/10.**

Риск «окирпичивания» роутера — **низкий**: изоляция сделана правильно (своя таблица `inet openstream`, чужие файлы не трогаются, `stop_service` убирает за собой, есть откат dnsmasq). Физического вреда устройству архитектура не наносит.

Но **основная функциональность 2.1 на реальном роутере не работает** — не из-за логики, а из-за разрыва в упаковке. Плюс найдены **две RCE-инъекции от root** и **фиктивная система обновлений**.

Ключевой вывод: продукт выглядит завершённым в документации и в UI, но сквозной путь «правило → nftables → трафик» разорван минимум в четырёх местах. Это не «полировка», а восстановление станового хребта.

## 🔴 BLOCKER — функциональность физически не доезжает до роутера

### B1. `openstream-render.uc` не устанавливается пакетом

`package/openwrt/Makefile` (секция `Package/openstream-engine/install`) устанавливает 6 скриптов в `/usr/libexec/`, но **`openstream-render.uc` среди них нет**. При этом на него ссылаются по трём разным путям:

| Кто | Ожидаемый путь | Существует |
|---|---|---|
| `streamproxyd.init:285` | `/usr/libexec/openstream-render.uc` | ❌ |
| `openstream.uc:728,772` (RPC) | `/usr/share/openstream/openstream-render.uc` | ❌ |
| Файл в репозитории | `package/openwrt/files/openstream-render.uc` | ✅ (не упакован) |

Следствие: проверка `[ -x /usr/libexec/openstream-render.uc ]` всегда ложна → init молча уходит в fallback. RPC-вызовы `save_routing`/применения настроек вызывают несуществующий файл через `system(... 2>/dev/null || true)` → **тихо не делают ничего**, но возвращают `success: true`.

### B2. Правила `.osrule.yaml` не попадают в пакет

В Makefile **нет ни одной строки установки `rules/`**. Каталоги, которые ожидает код:

- `streamproxyd.init:291` → `/usr/share/openstream/rules` (не создаётся, не наполняется)
- RPC + render.uc → `/etc/openstream/rules` (не создаётся, не наполняется)

Fallback в init: `elif [ -x "$PROG" ] && [ -d "/usr/share/openstream/rules" ]` — каталога нет → **условие ложно → `--compile-rules` не запускается никогда**.

Итог B1+B2: **весь декларативный слой правил — ядро концепции продукта — на реальной установке не активируется вообще.** Работают только захардкоженные Twitch-пресеты в `apply_dnsmasq` (строки 242–282 init).

### B3. Два разных каталога правил — RPC пишет туда, откуда init не читает

RPC `save_routing` (`openstream.uc:196`) пишет в `/etc/openstream/rules`, init читает `/usr/share/openstream/rules`. Даже если B1/B2 починить, правила, сохранённые из веб-интерфейса, не будут прочитаны init-скриптом. Пути нужно свести к одному.

### B4. Сгенерированный nftables не загрузится — `redirect` в filter-цепочке

Оба генератора выдают `redirect` внутри цепочки типа `filter`:

```
chain mangle_prerouting {
    type filter hook prerouting priority mangle - 5;   # ← filter
    ...
    ip daddr @streamproxy_targets tcp dport { 80, 443 } redirect to :8888   # ← NAT-действие
}
```

Источники: `crates/openstream-backend-openwrt/src/nftables.rs:104,152` и `package/openwrt/files/openstream-render.uc:93,108`.

`redirect` — NAT-statement, допустим только в цепочке `type nat`. В filter-цепочке `nft -f` завершится ошибкой и **не применит файл целиком** — вместе с bypass, zapret2 и vpn-правилами.

В `render.uc` эта строка выводится **безусловно** (нет проверки на пустой список) → файл `/tmp/openstream.nft` невалиден всегда.

Ошибка замаскирована: `nft -f "/tmp/openstream.nft" 2>/dev/null || true` (`init:288`) — падение не логируется и не видно администратору.

### B5. `reject` в prerouting — вторая ошибка загрузки

`nftables.rs:127,132`: `udp dport 443 reject` и `tcp dport 853 reject` в цепочке с `hook prerouting`. `reject` поддерживается только в `input`/`forward`/`output`. При включённых `disable_quic`/`block_doh` — ещё одна причина отказа загрузки всего файла.

> Замечание о верификации: B4/B5 определены статически по спецификации nftables; на живом роутере не проверялись. Проверка одной командой: `nft -c -f /tmp/openstream.nft` (флаг `-c` — dry-run без применения).

### B6. Действие `Proxy` (VPN) не доведено до конца — маршрутизация по метке отсутствует

Правило `ip daddr @vpn_default mark set 0x00880001` ставит метку. Но по всему репозиторию **нет ни одного**:

- `tproxy` statement в nftables (проверено: `grep -rn "tproxy to"` — пусто);
- `ip rule add fwmark ... lookup ...`;
- `ip route add local default dev lo table ...`.

`sing-box` при этом слушает 10888 (`singbox.rs:145,255`). Метка ставится, но политики маршрутизации, которая направила бы помеченный пакет в TPROXY-сокет, не создаётся нигде. **Помеченный пакет уходит обычным маршрутом в WAN.** Заявленное в README «Туннелирование sing-box с привязкой к TPROXY :10888» на уровне OpenWrt-бэкенда не реализовано.

### B7. Защита от петель не срабатывает — `ct mark` проверяется, но никогда не ставится

`nftables.rs:107`: `ct mark & 0x00ff0000 == 0x00880000 return` — проверяется **connmark**. А устанавливается `meta mark` (`mark set 0x00880001`). `ct mark set` не встречается в репозитории ни разу (проверено grep). Без `ct mark set meta mark` условие никогда не истинно → заявленная «защита от петель и переполнения conntrack (#74)» фактически отсутствует.

## 🔴 CRITICAL — безопасность

### S1. Command injection от root через `import_subscription`

`luci-app-openstream/root/usr/share/rpcd/ucode/openstream.uc:484`:

```js
let pipe = fs.popen('curl -s -k -L --max-time 15 -H "User-Agent: ' + ua + '"'
                    + hwid_hdr + ' "' + input + '" 2>/dev/null', 'r');
```

`input`, `ua` (`user_agent`), `hwid` приходят из RPC-аргументов. Единственная проверка `input` — `match(input, /^https?:\/\//)`, что не мешает добавить кавычку и метасимволы дальше в строке. `ua` и `hwid` не валидируются вообще.

Пример полезной нагрузки в `user_agent`: `X"; <произвольная команда>; echo "`. rpcd работает от root → **выполнение произвольных команд с правами root**.

Дополнительно: `curl -k` отключает проверку TLS-сертификата — подписка загружается без защиты от MITM.

### S2. Command injection от root через `test_server_latency`

`openstream.uc:628`:

```js
let pipe = fs.popen('nc -z -w 2 ' + srv + ' ' + port + ' 2>/dev/null && echo OK', 'r');
```

`srv` не валидируется ничем (`port` безопасен — приведён через `int()`). Тот же результат: root RCE.

### S3. ACL даёт доступ к уязвимым методам

`luci-app-openstream/root/usr/share/rpcd/acl.d/luci-app-openstream.json` выдаёт `"openstream": [ "*" ]` и на чтение, и на запись. Методы `import_subscription` и `test_server_latency` не перечислены в более строгом `luci/acl.d`, но wildcard в rpcd-ACL их покрывает.

Эксплуатация требует аутентификации в LuCI, то есть это **post-auth**. Но это полноценная эскалация: пользователь LuCI с ролью openstream → root shell. Для роутера с несколькими администраторами или при краже сессии — критично.

### S4. SECURITY.md утверждает обратное

Цитата: «Серверный RPC плагин `openstream.uc` строго валидирует входные параметры регулярными выражениями и не передает нефильтрованные пользовательские данные в системные shell-вызовы». Это **прямо противоречит** S1/S2. Документ даёт ложное чувство защищённости.

Справедливости ради: в других местах валидация сделана хорошо — `save_routing:202` (whitelist имени файла), `test_route:230`, домены в `render.uc:144`, `dns_hosts:119`. Проблема точечная, но критичная.

### S5. Значения `bypass_cidrs` / `bypass_clients` не валидируются

`render.uc:54-75` и `nftables.rs:34-36,88` подставляют значения из UCI в nft-файл без проверки формата (в отличие от доменов рядом). Некорректное значение из LuCI ломает загрузку **всей** таблицы — с учётом B4 это ещё один путь к молчаливому отказу маршрутизации.

## 🟠 HIGH — ложная функциональность

### F1. `perform_update` — полностью фиктивная

`openstream.uc:1063-1095`. Функция пишет в лог:

```
[дата] Загрузка проверочных контрольных сумм SHA256... OK
[дата] Обновление sing-box до последней версии... Успешно.
[дата] Компонент [all] успешно обновлен и синхронизирован!
```

…и возвращает `success: true`. **Ни одной операции скачивания, проверки контрольной суммы или установки в коде нет.** Пользователь видит успешный лог и остаётся на старой версии sing-box/zapret2, считая, что обновился. Для компонентов безопасности это опасная иллюзия.

README (п.5) заявляет «Cron Автообновление с проверкой контрольных сумм SHA-256 и безопасным откатом». Ничего из этого не реализовано.

### F2. `check_updates` — захардкоженные версии

`openstream.uc:1013-1052`: `installed_version: '0.4.2-35'`, `latest_version: '1.12.1'`, `update_available: true` — литералы. Никакого обращения к сети или `opkg`. Всегда сообщает о доступных обновлениях sing-box и zapret2 независимо от реальности.

### F3. Cron указывает на несуществующий бинарник

`openstream.uc:807`: `0 4 * * * /usr/bin/openstream-autoupdate`. Файла `openstream-autoupdate` **нет нигде в репозитории** (проверено `find`). Задание будет ежедневно падать с `not found`.

### F4. `switch_singbox_variant` ничего не переключает

`openstream.uc:985-1007`: записывает значение в UCI и пишет в лог «Вариант успешно переключен». Скачивания/замены бинарника нет. README обещает 4 сборки sing-box с переключением в 1 клик.

### F5. Мониторинг показывает выдуманные цифры

`openstream.uc:327-328`:
```js
packets: 120 + int(rand() % 400),
bytes:  184000 + int(rand() % 950000),
```
«Живой трафик» в LuCI — случайные числа, не счётчики nftables. Также `:637` и `:657` — случайная задержка вместо реального замера при неудаче.

### F6. Лог обновлений затирается

Во всех местах используется `writefile` (перезапись), а не дозапись. Каждая следующая строка стирает предыдущую — в логе остаётся только последняя.

## 🟡 MEDIUM — надёжность и риск потери данных

### M1. `CRON_MARK` не определена — дубликаты в crontab

`streamproxyd.init` использует `$CRON_MARK` в трёх местах (352, 355, 415), но **переменная нигде не задаётся** (в отличие от `HOSTS_MARK`). Последствия:

- `sed -i "\|$CRON_MARK|d"` превращается в `sed -i "\||d"` — пустой шаблон, поведение зависит от реализации sed (в busybox — либо ошибка, либо повторное использование последнего regex);
- добавляемая строка не содержит маркера → при каждом `reload` **в crontab добавляется новая копия** задания `openstream-update-hostlists`;
- `stop_service` не может удалить своё задание.

### M2. Перезапись `/etc/crontabs/root` целиком

`openstream.uc:808-816`: читает crontab, фильтрует, записывает обратно целиком. Если `readfile` вернёт пусто при временной ошибке — **чужие задания пользователя будут стёрты**. Нужна проверка на успешность чтения перед перезаписью.

### M3. Конфликт имени таблицы: transparent-режим против render

Оба используют `inet openstream`:
- `openstream.nft` (статический): NAT-цепочка `prerouting` + сет `openstream_hls`;
- `render.uc` / `nftables.rs`: `delete table inet openstream` и создание своей структуры **без** `openstream_hls`.

Порядок в `start_service`: `apply_transparent_nft` → `apply_dnsmasq` (→ render). То есть при `mode=transparent` только что созданная таблица **немедленно удаляется** следующим шагом. Скрипт `openstream-refresh-hls-set` затем пытается наполнить несуществующий сет. Заявление COEXISTENCE.md о бесконфликтности внутри самого проекта не выполняется.

### M4. `delete table` на каждом рендере сбрасывает динамические сеты

Сеты `bypass_targets`, `zapret2_targets`, `vpn_default` наполняются dnsmasq через `nftset=` **в момент DNS-резолва**. Пересоздание таблицы очищает их. Пока записи в DNS-кэше клиентов живы, повторного резолва не будет → домены «выпадают» из маршрутизации на время TTL. Нужен инкрементальный `flush set` вместо `delete table`, либо форсированная перерезолвка.

### M5. `$VPNSET` не определена в uci2yaml

`package/openwrt/files/openstream-uci2yaml:80`: `[ -n "$VPNSET" ] && echo "geo_split_vpn_set: ..."`. Определены `VPNSET_EU`, `VPNSET_ADFREE`, `VPNSET_CUSTOM`, но не `VPNSET`. Условие всегда ложно → **`geo_split_vpn_set` никогда не попадает в `config.yaml`**. Та же природа бага, что и M1.

### M6. Цепочка `openstream_tproxy` не решает заявленную задачу (#84)

`type filter hook input priority filter - 1; policy accept` + `accept` для портов 8888/1088. Замысел — обойти `input REJECT` в гостевых зонах fw4.

В nftables `accept` в одной base-цепочке **не отменяет** вердикт другой base-цепочки на том же хуке: пакет продолжает обход всех base-цепочек в порядке приоритета, и последующий `reject` в fw4 всё равно сработает. Немедленно завершает обработку только `drop`. То есть «решение #84» с высокой вероятностью — **no-op**.

(Побочный плюс: раз это no-op, то и опасения о непреднамеренном открытии портов в WAN беспочвенны.)

### M7. Ошибки загрузки правил проглатываются

`compile_rules_dir` (`openstream-backend-openwrt/src/lib.rs:40,47`): `if let Ok(rule) = load_rule_file(...)`. Невалидное правило пропускается **без единого сообщения**. Администратор не узнает, что его правило не применилось.

### M8. 91 `unwrap()`/`expect()`/`panic!` вне тестов при `panic = "abort"`

`Cargo.toml` задаёт `panic = "abort"` в release. Любой `unwrap()` на неожиданных данных — немедленное падение процесса. Смягчающее обстоятельство: `procd_set_param respawn 3600 5 0` (threshold 0 = не сдаваться) — сервис перезапустится, блокировки не будет. Но это лечение симптома.

## 🟢 Что сделано правильно

Справедливая часть — здесь архитектурные решения действительно грамотные:

1. **Изоляция nftables.** Своя таблица `inet openstream`, `inet fw4`/`inet zapret` не трогаются. `stop_service` удаляет только свою таблицу. Это главная причина низкого риска для роутера.
2. **`safe_dnsmasq_reload`** (`init:169-183`) — `dnsmasq --test` перед применением, удаление своего конфига и повторный старт при неудаче. Защита от потери DNS на роутере сделана правильно.
3. **Аккуратная работа с чужими файлами.** Маркер `# openstream` в `/etc/hosts`, точечное удаление своих строк, чужие `.conf` в `dnsmasq.d` не трогаются.
4. **Атомарная запись** — `uci2yaml` пишет в `$TMP` и делает `mv`; конфиг dnsmasq сравнивается через `cmp` и dnsmasq не перезапускается впустую.
5. **Валидация там, где она есть** — whitelist имени файла правила (`:202`), regex доменов с проверкой на `..` и длину (`render.uc:144`), `tr -cd` для имён сетов.
6. **`uci-defaults` безопасен** — трогает только свою секцию UCI, содержит комментарий о ранее исправленном баге с `add_list confdir`.
7. **Автоопределение соседских сетов** (`detect_vpn_set`) — разумный подход к сосуществованию с Podkop/Forkop/PassWall.
8. **Rust-ядро**: 1 `unsafe` на 24 крейта, строгая типизация, SecOps-валидатор защищённых доменов с тестами, CI с `clippy -D warnings`.
9. **`procd respawn` с threshold 0** — осознанное решение против crash-loop lockout, с комментарием в коде.

## Сравнение с forkop

Референс вендорён в `research/references/forkop/`. Архитектурное преимущество OpenStream реально: декларативные `.osrule.yaml`, кроссплатформенное Rust-ядро, разделение действий (bypass/zapret2/proxy/block) — у forkop такого слоя нет.

Но forkop **работает**, а описанный выше разрыв упаковки означает, что OpenStream на реальном роутере сейчас — набор Twitch-пресетов из init-скрипта. Чтобы «превзойти forkop», нужно сначала довести до работоспособности то, что уже спроектировано.

## План приведения к продакшену

### Этап 1 — восстановить работоспособность (блокеры)
1. Добавить в Makefile установку `openstream-render.uc` и каталога `rules/*.osrule.yaml`.
2. Свести пути к одному: каталог правил и путь к render.uc (init, RPC, render).
3. Исправить B4: вынести `redirect` в отдельную цепочку `type nat hook prerouting`.
4. Исправить B5: перенести `reject` в `input`/`forward`.
5. Реализовать маршрутизацию по метке (`ip rule`/`ip route`) либо `tproxy` statement — иначе действие Proxy нерабочее.
6. Добавить `ct mark set meta mark` или изменить проверку на `meta mark`.
7. Убрать `2>/dev/null` с `nft -f`, логировать ошибку через `logger -p daemon.err`.
8. Добавить `nft -c -f` (dry-run) перед реальным применением — по аналогии с `dnsmasq --test`.

### Этап 2 — безопасность
9. Переписать `import_subscription` и `test_server_latency` без конкатенации в shell: валидация по whitelist + передача аргументов массивом, а не строкой.
10. Убрать `curl -k`.
11. Сузить ACL: заменить `"openstream": ["*"]` на явный список методов, разделив read/write.
12. Привести SECURITY.md в соответствие с фактом.
13. Валидировать `bypass_cidrs`/`bypass_clients` как CIDR/IP.

### Этап 3 — убрать ложную функциональность
14. Реализовать `perform_update`/`check_updates` **или** явно пометить как «не реализовано» и скрыть из UI. Текущее состояние хуже обоих вариантов.
15. Либо добавить `openstream-autoupdate` в пакет, либо не прописывать cron.
16. Заменить `rand()` в мониторе на реальные счётчики nftables (`nft -j list counters`) либо убрать показатель.
17. Исправить дозапись лога (append вместо перезаписи).

### Этап 4 — надёжность

## Ответы на поставленные вопросы

**Всё ли работает?** Нет. Декларативный слой правил не активируется на реальной установке (B1–B3), генерируемый nftables не загружается (B4–B5), действие Proxy не доведено до маршрутизации (B6).

**Есть ли конфликты?** С чужими пакетами (fw4, zapret, podkop) — архитектурно нет, изоляция сделана хорошо. Внутри проекта — да: transparent-режим и render борются за одну таблицу (M3).

**Качество кода?** Rust-ядро — хорошее (типизация, тесты, 1 unsafe, чистый clippy в CI). ucode RPC — слабое место: инъекции, фиктивные функции, выдуманные данные. Shell — три бага из-за неопределённых переменных (`CRON_MARK`, `VPNSET`).

**Риск повреждения роутера?** Низкий. Изоляция таблиц, откат dnsmasq, аккуратная работа с чужими файлами, respawn без lockout. Реальные риски — потеря пользовательских cron-заданий (M2) и накопление дубликатов (M1), а не порча ОС.

**Готовность к продакшену?** 3/10. Архитектура и замысел — сильные, реализация ядра — достойная, но сквозной путь разорван, и есть root RCE. После этапов 1–3 — можно говорить о бете; после 4–5 — о продакшене.
